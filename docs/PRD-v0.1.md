# Light-PS 产品需求与决策稿 v0.1

日期：2026-09-20。状态：产品定位已按用户纠正更新；功能覆盖与 PSD 兼容目标待对齐，技术选型未冻结，也未开始产品实现。

## 0. 一句话定位与当前假设

**一个可独立使用、成熟实用的在线 PS：产品形态与编辑能力参考 Photopea，UI 参考 Compositor 的原生 Mac / Swift 设计风格，同时提供 Agent、harness、节点画布和 Figma 接入。**

用户已明确：参考 Compositor 的轻量思路；需要实用、成熟的产品；应能连接不同 Agent、harness、节点画布和 Figma；结构需要提前想清楚。原始 PRD 是参考材料，其中技术限制不视为已确认决策。

用户明确纠正：核心诉求始终是在线 PS，Photopea 是成熟产品参照，Compositor 是 UI 风格参照。此前助手将高频使用场景 C 过度推导成“宿主优先的插件产品”，该定位与以宿主集成为首发前提的安排撤回。

用户仍需要 A（Agent 发起编辑）、B（编辑器调用 Agent）、C（与现有工具往返），C 更常见，相关工具为 TapNow、LightAI。这些是编辑器的扩展场景，不替代产品本体，也不让第三方平台接口成为独立编辑功能上线的前提。

产品默认在浏览器中直接使用；编辑可在设备本地完成。Compositor 的视觉和交互方向用 Web 技术实现，不因参考 Swift 风格就改成 Swift/macOS 应用。是否使用已有编辑内核、以及 PSD 的兼容深度，均待单独评估。[Photopea 产品说明](https://www.photopea.com/learn/)、[Compositor 官网](https://robbietilton.com/compositor)

功能参照不等于已经要求逐项复刻 Photopea。图层、选区、蒙版、画笔、变换、调色、裁切、保存导出构成编辑主体；文字、基础形状、修复工具、图层组与 PSD 兼容应按日常任务确认，不能继续套用原始微型合成节点的严格排除项。也不把 Photopea 当作已选定或可任意换肤的底层实现。

本产品中的“轻量”首先指打开快、常用操作短、依赖少、学习成本低。包体积是工程预算，不能通过牺牲保存、撤销或输出正确性来达成。

## 1. Problem Statement：用户真正需要完成的工作

用户需要一个打开浏览器即可使用、界面简洁而常用编辑能力扎实的在线 PS，能独立完成图片编辑并可靠保存工程。连接生成工具是附加价值：减少素材搬运，保留坐标、尺寸、版本与来源，方便继续编辑。

优先服务三类工作：

| 工作 | 用户要控制什么 | 产品交付什么 |
|---|---|---|
| 多素材合成 | 主体位置、尺度、边缘、明暗和遮挡 | 可继续修改的工程与合成图 |
| 局部生成后修整 | 修改范围、上下文、候选结果和接缝 | 对齐原位置的结果图层及来源记录 |
| 跨工具往返 | 哪一版送出、发到哪里、结果写回哪里 | 一次明确提交与可重试的交付记录 |

首批对象是日常需要图片编辑的设计师、内容创作者，也包括使用生成式图像工具的用户。专业印刷与团队实时协作暂不作为首发建议，普通编辑体验不依赖 Agent 或节点平台。

## 2. Solution：完整工作流程

首要验收流程：打开网页 → 新建工程或导入文件 → 使用图层、选区、笔刷、蒙版等工具完成编辑 → 保存工程和导出 → 重新打开继续编辑。整个流程不要求连接任何 Agent、节点画布或本地服务。

TapNow/LightAI 的画布读取和写回能力仍需验证，作为独立的接入工作推进。此前“独立窗口还是必须页内编辑”的追问退出当前主线，优先确认在线 PS 本身的功能与文件兼容要求。

### 2.1 共享编辑流程：合成 → 局部处理 → 接回 → 再编辑

1. 拖入或粘贴多张素材；创建或打开工程。
2. 排列、缩放、旋转、混合，使用图层蒙版修边，按需调整颜色。
3. 选中需要修改的区域，选择已连接的处理工具，填写任务说明。
4. 编辑器冻结本次输入版本，发送图片、遮罩和位置映射；用户能看到目的地与发送范围。
5. 任务运行期间，用户可以继续编辑；后续编辑不改变已发送的输入。
6. 返回结果作为候选；用户对比后接收为新图层。若工程已变更，提示它基于旧版本，不静默覆盖。
7. 用户继续修边，保存工程，导出或提交给原宿主。

首发先支持全画布图像与同尺寸遮罩往返，返回图也须匹配同一坐标系；局部裁切、补边及不同模型尺寸的自动回贴放在下一阶段。第一版的数据契约必须能表达这些映射。

### 2.2 Agent 发起、人工接手

Agent 创建工程、添加素材、安排初始位置 → 请求人工检查 → 用户修改并明确提交 → Agent 得到固定版本的产物 → 下游继续运行。用户取消或超时有独立状态，不能把“没有提交”误认作“执行成功”。

### 2.3 节点画布接入

宿主节点展示缩略图、输入状态和编辑入口；用户在弹窗或较大面板编辑。节点输出引用最近一次明确提交的版本。拖动画布、笔刷涂抹和每次自动保存都不触发整个工作流重新运行。

### 2.4 Figma 往返

用户在 Figma 选取图像或 Frame → 插件提取图片/渲染快照 → Light-PS 编辑 → 插件插入新图片或明确替换指定图片填充。

首版 Figma 接入以位图交换为边界，不承诺把 Figma 文本、约束、Auto Layout、效果和图层蒙版完整转换成可无损互改的工程。Figma 官方 Plugin API 支持编辑文档，其图片流程通过图片数据与节点填充实现；据此，本方案选择插件作为写回入口。[Plugin API](https://developers.figma.com/docs/plugins/)、[图片读写说明](https://developers.figma.com/docs/plugins/working-with-images/)

## 3. 对原 PRD 的关键修订

| 原始约定 | 建议修订 | 原因 |
|---|---|---|
| 纯前端页面提供本地 REST/WS 和文件监听 | Web 编辑器配可选本地伴随服务 | 浏览器编辑能力与操作系统服务有不同运行边界 |
| 全局 JS API 加文件监听即可接各种 Agent | 一个命令内核，分别提供 SDK、MCP、CLI/HTTP、宿主适配器 | 接口可被发现、可验证、可重试；具体宿主仍需适配 |
| 所有遮罩强制二值化 | 内部保留灰度，导出时按目标能力选二值、灰度或 Alpha | 柔边是合成需要，不同模型与节点的约定不一致 |
| 橡皮擦直接改源图 Alpha | 默认改可恢复的图层蒙版 | 反复修边不损坏源素材 |
| 一个独立 Mask 层 | 区分图层蒙版、当前选区、重绘区域 | 三者生命周期和坐标系不同 |
| 图层硬上限 10 | 按解码像素、缓存和历史内存准入 | 一张超大素材也可能比几十张小素材重 |
| 同步返回两份 Base64 | 异步生成带版本和校验信息的产物清单 | 减少大字符串复制，允许取消、进度和错误处理 |
| 全局 isCompleted | 每个任务、每次提交各有 ID 和状态 | 避免连续任务读到上一次的完成结果 |
| 一个固定输入/输出目录 | 按任务和提交隔离，完整写入后再发布完成状态 | 避免并发覆盖和读到半个文件 |
| 根容器阻断全部事件 | 仅在编辑器拥有焦点及处理手势时接管 | 保留文本输入、宿主快捷键和正常滚动 |
| 设置 crossOrigin 即解决跨域 | 必须源站允许，或先通过已授权资产导入 | 编辑器自身的 CORS 配置不能替外站授权 |
| 最后再做协议 | 第一条闭环就通过统一命令操作 | 防止 UI 与 Agent 形成两套行为 |

ComfyUI 官方资料明确存在介于 0 与 1 之间的遮罩值；其 LoadImage 节点还会从 Alpha 反向生成 MASK。因此不能假定“黑白 PNG 连到任意输入就正确”。[ComfyUI 图像与遮罩](https://docs.comfy.org/custom-nodes/backend/images_and_masks/)

Canvas 的跨域可读性取决于图片源站是否允许跨域访问。[MDN Canvas 图片说明](https://developer.mozilla.org/en-US/docs/Web/API/Canvas_API/Tutorial/Using_images)

## 4. User Stories：用户故事

1. 作为创作者，我希望不登录也能完成本地编辑，使日常修图不依赖账号和云服务。
2. 作为创作者，我希望拖入、粘贴或从已有工具接收图片，使导入不打断工作。
3. 作为创作者，我希望指定画布像素尺寸，缩放界面时不改变最终尺寸。
4. 作为创作者，我希望复制、重命名、排序、隐藏和锁定图层，使素材容易管理。
5. 作为创作者，我希望精确输入位置、尺寸、旋转并进行翻转，使布局可重复。
6. 作为创作者，我希望替换素材时可以保留布局，使更换生成候选不必重排。
7. 作为创作者，我希望混合模式、不透明度和基础调整能随时撤回，使融图可逐步尝试。
8. 作为创作者，我希望擦掉的边缘能够刷回，使修边不破坏原图。
9. 作为创作者，我希望矩形、套索和笔刷可以形成选区，使局部处理不必全靠手涂。
10. 作为创作者，我希望清楚知道当前笔刷作用于图像蒙版还是重绘区域，避免误操作。
11. 作为创作者，我希望裁切画布后仍能恢复画布外内容，使重新构图安全。
12. 作为创作者，我希望一笔、一段拖动或一次 Agent 批处理只算一次撤销。
13. 作为创作者，我希望自动保存、显式保存和提交的状态分得清楚，知道哪些修改已经保留。
14. 作为创作者，我希望重开工程后保留素材、蒙版、调整与来源，而不只得到平面 PNG。
15. 作为创作者，我希望发送任务前看到目标、范围和任务说明，使外部处理可控。
16. 作为创作者，我希望生成期间仍可编辑，迟到结果也不会盖掉新修改。
17. 作为创作者，我希望比较候选后接收为新图层，使不同方案可以继续组合。
18. 作为创作者，我希望断线和失败后能够重试或另存工程，避免工作丢失。
19. 作为 Agent 使用者，我希望查询结构化图层信息与带版本的预览，使工具能理解当前图像。
20. 作为 Agent 使用者，我希望批量编辑有事务、冲突检测和撤销，使自动化行为可追踪。
21. 作为 Agent 使用者，我希望明确区分任务等待、人工处理、成功、失败与取消，避免无限轮询。
22. 作为宿主开发者，我希望嵌入接口与界面实现解耦，使应用升级不需要重新对接所有编辑操作。
23. 作为节点用户，我希望仅在明确提交后更新下游，使绘画过程不反复触发昂贵生成。
24. 作为 Figma 用户，我希望回写到正确对象；原对象被删除或改动时提示冲突。
25. 作为接入方，我希望获得能力、版本、尺寸与遮罩约定，使不兼容请求在执行前得到解释。
26. 作为用户，我希望大图、缺失资源和不支持格式在导入时被说明，而不是导出时才失败。

## 5. 功能范围与发布分层

### 5.1 R1：首个可独立日常使用的在线编辑器

以下是现有编辑基础与扩展方向。独立编辑、工程可靠性为首发基线；文字/图形/PSD 等能力须按新的产品参照补充评审，原有微型合成节点范围不再视为完整 R1。

| 模块 | R1 必须具备 | 验收重点 |
|---|---|---|
| 工程 | 新建、打开、自包含工程保存、另存、自动保存、崩溃恢复 | 重开后的图层与像素一致；保存失败可见 |
| 素材 | PNG/JPEG/WebP 静态图片，拖入、粘贴、缺失资源提示 | EXIF 方向正确、导入尺寸已知、源文件保留 |
| 画布 | 固定像素尺寸，裁切/扩边，平移、缩放、适应窗口 | 视口、DPR 不影响导出尺寸 |
| 图层 | 添加、删除、复制、替换、排序、显隐、锁定、命名 | ID 稳定；替换时明确保留布局或使用原尺寸 |
| 变换 | 移动、等比/自由缩放、旋转、翻转、数值输入、基本吸附 | 小数坐标、负缩放和越界行为一致 |
| 融图 | 原稿 8 种混合模式、不透明度、亮度/对比度/饱和度 | 预览与导出遵循同一处理顺序 |
| 局部编辑 | 图层蒙版、可恢复擦除、矩形/套索/画笔选区、反选与羽化 | 明确编辑目标，图层变换后蒙版仍对齐 |
| 历史 | 一次手势一条历史、Agent 批处理一条历史、内存预算 | 撤销恢复可见结果；不按 pointermove 存全图 |
| 交付 | PNG 合成图、JPEG 背景填充、二值/灰度 Mask、工程文件 | 固定版本、明确颜色和 Alpha 规则 |
| 扩展接口 | 为 Agent 与宿主提供统一命令、查询、预览和产物契约 | 与人工操作共用校验及历史；具体适配器单独验收 |

外部处理连接器随首个节点宿主与用户实际 Agent 工作流确定。JS SDK、MCP、CLI/HTTP 是不同接入选项，不强制首版把每一种传输都做全。没有真实连接器时，手动导出与导入仍可用，但不能据此声称“完整双向 Agent 协作”已经交付。

普通编辑从网页直接开始。需要宿主适配或深度本地自动化时，再按连接目标提供插件或本地组件；这些组件不成为基础修图的安装前提。

### 5.2 R2：接入与局部生成增强

- Agent/harness 双向往返：结构化读取、预览、批量命令、任务状态与结果导入；至少一种真实目标完成验收。
- TapNow/LightAI 等节点宿主适配，依据实际开放能力验证，保留不能接入时的普通文件交换。
- Figma 插件：选择导出、图像编辑、插入或替换、冲突与失败恢复。
- 局部裁切、上下文边距、模型尺寸适配和精确回贴。
- 图层分组、多选变换、对齐/分布、可复用的命名选区。
- 扩展第二种 Agent/harness，以验证接入能力不是对单一工具硬编码。

独立编辑器与各类接入分别验收，只宣称实际完成的支持范围。功能覆盖以新的在线 PS 定位重新对齐，不能把所有产品价值压在第三方平台的接口上。

### 5.3 后续按真实使用数据决定

剪贴蒙版、更多调整、局部柔化/模糊、修复与仿制、PSD 部分导入、独立桌面封装。每项由实际任务阻塞情况决定顺序，不提前建立插件市场或复杂扩展平台。

## 6. 交互原则

工具栏只放当前可用工具；选择、蒙版修边与重绘范围的作用目标必须可见。吸管如仅能显示颜色值却不能用于工作，不因原稿列出就保留占位按钮。

右侧优先显示图层与当前对象属性；历史、连接和任务记录可折叠。独立模式区分“保存工程”“导出图片”“发送处理”；宿主模式突出“提交给宿主”，不使用含义模糊的通用“完成”。

快捷键使用平台对应的 Cmd/Ctrl；撤销重做优先采用系统习惯。画布拥有焦点时处理视口快捷键，输入框内不劫持文字编辑。缩放提供适应窗口、100% 和精确百分比；100% 定义为一图像像素对应一 CSS 像素，若另做设备像素查看须明确命名。

节点中放缩略预览和编辑按钮；提供足够大空间操作笔刷。宿主滚轮与编辑器手势协商，避免在狭小节点中嵌入整套密集工具栏。

UI 要能表达：未连接、导入中、素材损坏、内存不足、保存中/失败、等待人工、外部运行中、取消中、旧版本结果、回传失败。错误应给出下一步动作，而非只显示异常编号。

## 7. Implementation Decisions：实现决策建议

所有条目均为本稿建议，待基准验证与评审后冻结。

1. **独立工程模型。** 图层、资产、蒙版、调整与任务来源属于产品；Fabric/Konva 序列化结果不直接成为公开工程格式。
2. **一个命令入口。** 用户操作与 Agent 指令进入同一命令处理器，共用校验、版本、历史和事件；临时笔刷预览不逐点产生远程请求。
3. **单写者。** 每个工程只有一个权威编辑会话。第一版不实现多人 CRDT，也不允许多个 Agent 绕过版本检测直接改状态。
4. **像素与界面分离。** 渲染器负责合成，交互层负责选中框和手势，UI 不把整份像素缓冲放进响应式状态树。
5. **原素材保留。** 变换、调整、图层蒙版非破坏；导出时才得到合成像素。
6. **控制数据与图片数据分离。** 命令传 ID、参数和资产引用；图片走二进制通道。全局 API 是 SDK 的便利入口，不是主协议。
7. **任务产物不可变。** 提交绑定确定的工程版本；重做提交生成新 ID；任何候选结果都保留其输入来源。
8. **接入分两面。** Agent 调用编辑器由 MCP/CLI 等承接；编辑器调用外部处理由连接器承接。两者共用数据契约，但不假装所有 Agent 都能以同一种方式启动。
9. **保存是核心能力。** 浏览器本地缓存、可携带的工程包和伴随服务磁盘存储分别定义责任，不能把“缓存成功”描述成“永久保存”。浏览器存储受配额与清理策略影响。[MDN 存储说明](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)
10. **先验证渲染再锁库。** TypeScript + React 为建议应用栈；Canvas 2D 为首个验证后端，GPU 加速以实际基准为依据。Fabric/Konva 可提供交互能力，miniPaint 可作功能参考，尚无代码复用结论。

建议独立测试的模块为：工程命令、像素合成/蒙版、保存恢复、任务交付、宿主适配。具体协议和坐标规则见配套架构稿。

## 8. Testing Decisions：质量与发布门槛

以下是待验证目标，不是已经测得的性能。现有工作区没有此产品的代码或可复用测试，不能声称已验证。

### 8.1 正确性门槛

| 场景 | 必须得到的结果 |
|---|---|
| 两层半透明素材叠加，轮换 8 种混合模式 | 与固定参考样张在约定误差内一致 |
| 图层旋转、翻转、非等比缩放后擦除 | 蒙版准确对应原图；可刷回；撤销恢复 |
| 不同缩放与 DPR 下导出 2048×2048 | 产物始终为 2048×2048；不带红色遮罩覆盖层 |
| 二值遮罩导出 | 解码后 RGB 仅 0/255、通道一致，Alpha 恒为 255 |
| 灰度遮罩导出 | 保留软边；模型端极性转换有样张验证 |
| 保存后关闭、重开 | 资产、图层、调整、蒙版、坐标与来源可恢复 |
| 同一 Agent 请求重复发送 | 相同请求只生效一次，返回同一结果 |
| 人修改后 Agent 提交旧版本命令 | 返回版本冲突；当前工程无静默覆盖 |
| 外部结果在新一轮编辑后到达 | 标为旧输入候选，接收前不改变当前工程 |
| 写出中断、缺图、磁盘满 | 不发布成功清单；可继续编辑或导出恢复包 |
| 节点重试与刷新 | 不重复执行昂贵生成，不误用旧提交 |
| Figma 原节点被移动/修改/删除 | 不猜测替换对象；可插入新图或报告冲突 |

测试聚焦外部行为和用户可观察结果，不写与内部代码结构一一对应的测试。像素测试采用解码图像比较，避免把 PNG 编码器差异误判为图像差异。

### 8.2 性能与容量基线

首轮基准建议固定在 Apple M1 / 16 GB、发布时锁定的 Chrome 稳定版；另做 Windows / Edge 验证。记录完整版本及显示缩放，不把设备名称当作全部测试环境。

- 标准样张：2048×2048，10 个同尺寸素材图层，含透明、4 个图层蒙版、3 个基础调整。
- 连续拖动目标：帧时间 p95 不高于 33 ms；一般交互响应 p95 不高于 100 ms。
- 标准样张全尺寸 PNG 导出目标：5 秒内；超过 1 秒显示进度，能取消。
- 初始可交互代码与样式网络传输目标：gzip 后不高于 1.5 MB；按需模块、图片与本地服务单独核算。基准前不承诺总安装包达到此值。
- 空白文档首次可交互目标：在约定本地冷启动环境下 2 秒内。
- 容量资格测试覆盖单边最高 4096 像素的文档，但输入总解码量、单素材像素与缓存仍需准入；超限明确提示，不静默缩小最终输出。
- 标准样张编辑进程内存增量目标不高于 1 GiB；同时计入进程外 GPU 使用观察。历史、纹理和临时缓冲分别设预算。
- 连续执行 100 次“载入—编辑—关闭”后，检查资源释放与内存趋势，不能只看第一次流畅。

若基准无法达到目标，先分析缓存与脏区域更新；必要时更换渲染后端。不能先宣布“不支持实际工作需要的大图”来使测试通过。

### 8.3 可用性门槛

邀请 5–8 位目标用户完成三个真实任务：多素材合成、局部重绘往返、重开工程继续改。记录成功率、完成时间、手动导入导出次数和中途退出原因。

首要产品指标是“任务成功完成且工程可继续修改”；效率与现有实际流程比较。无基线前不宣称减少某个百分比。使用记录默认本地；产品遥测若引入，另行明确开关和数据范围。

## 9. 交付路径：按可验证的完整流程推进

| 阶段 | 交付物 | 通过后才继续 |
|---|---|---|
| A：功能与关键风险验证 | Photopea 常用能力范围、PSD 目标；软蒙版、混合导出、性能与恢复 | 先确定日常任务与文件兼容深度，再冻结内核 |
| B：第一条真实闭环 | 打开网页 → 导入 → 编辑 → 保存重开 → 导出；UI/SDK 走同一命令 | 独立编辑、正确性与恢复测试通过 |
| C：R1 发布加固 | Compositor 风格界面、快捷键、错误恢复、真实编辑任务试用 | 达到冻结后的 R1 编辑范围与发布门槛 |
| D：Agent 扩展闭环 | Agent 发起 → 人编辑 → 提交 → Agent 读产物；外部处理结果接回 | 重试、断线、取消、旧版本结果测试通过 |
| E：宿主扩展 | 节点画布、Figma 插件及裁切回贴 | 各自宿主契约和回归样张通过 |

不以“工具栏都画出来了”作为完成标准；也不按未知团队规模给出固定工期。阶段 A 后才做有依据的排期。

## 10. Out of Scope：明确不在首发范围

- 不默认承诺完整 Photoshop/Photopea 的全部功能。PSD 兼容深度待确认，不能先排除，也不能提前承诺完全无损往返。
- 专业印刷级 CMYK、16/32 位 HDR、RAW、3D 与视频时间线暂不作为首发建议。常用文字与基础图形重新纳入范围评审，不沿用旧稿的统一排除。
- 自建通用节点编排器、通用 Agent harness、模型训练和模型托管。
- 多人实时协作、组织权限后台、插件商城和公共云素材库。
- 关闭浏览器后仍能进行所有像素编辑/导出的无界面服务承诺；第一版任务应明确报告所需编辑会话。

## 11. Further Notes：仍需冻结的决策

1. Photopea 常用能力中哪些属于首发刚需；首先确认 PSD 是否需要保留图层导入并保存回 PSD。
2. Compositor UI 的具体布局和交互偏好；TapNow/LightAI 与 Agent 接入之后单独对齐，不继续用宿主问题替代产品本体讨论。
3. 首批素材分辨率、典型图层数与目标设备；用样张替代想象中的容量需求。
4. 首发桌面浏览器支持范围、个人/团队使用方式；桌面安装包仅作为未来选项。
5. 后续是否有 PSD、文字和复杂修复的高频任务；如果有，重新评估边界与复用现有编辑器的收益。
